Sentinel is a real platform, not a dashboard shell. The eBPF TLS-capture sensor, the four-agent detection pipeline, and the versioned risk model are genuine engineering with 1,108 backend tests behind them. That is a stronger foundation than the positioning problem suggests.

Two things block the story it tells. The Evidence Engine — the product's stated moat — is one list endpoint over two tables. And there is no AI investigation layer at all, which makes "AI-Native" the single least defensible claim on the page.

01

Current architecture

FastAPI monolith, React SPA, eBPF sensor, single Postgres. Deliberate and coherent — not accidental.

The request path is a single aggregate router mounted at /api, fronted by an AdaptiveRequestGuard middleware. Fifty-five feature routers cover 55 surfaces; behaviour lives in 44 modules under server/modules/, which is the right separation and is mostly honoured.

Two routes sit deliberately outside /api: POST /v1/events and a legacy POST /, both authenticated with a sensor API key rather than a user JWT. That is the eBPF ingest path, and it is the most differentiated part of the system.

The detection pipeline is real

This is not rule-matching dressed up as a pipeline. Four named agents run in sequence over eleven detectors (BOLA, BFLA, injection, exfiltration, burst, bot, auth-anomaly, behavioural-baseline, resource-abuse, schema, plus common), and the unified pipeline is running in active mode in production — it owns alerts and evidence, not just observation.

SourceeBPF sensor, logs, OpenAPI, recon
NormalizeNormalizationAgent → envelope
DetectRuleDetectionAgent → 11 detectors
CorrelateCorrelationAgent → incident
EnforceEnforcementAgent → block / rate-limit
InvestigateNot built — no AI layer exists

The sensor is the hard part, and it works

A C BPF program with OpenSSL and Go TLS uprobes, shipped by a Rust/Tokio userspace agent that parses HTTP/1.1 and HTTP/2, redacts PII, and gzip-batches to /v1/events. It captures decrypted TLS traffic at the kernel boundary with no proxy, no sidecar, and no certificate games. Most competitors need a mirror, a gateway plugin, or an inline proxy to get the same data.

Ingest correctly preserves request/response bodies and JWT identity through normalization, drops the console's own self-traffic, and coerces sensor clock skew. Those are the details that separate a demo from a product.

Data flow is disciplined: pages → hooks → services → api-client, with no fetch in pages and no localStorage — the httpOnly cookie is the real session. Realtime invalidation replaces polling entirely (refetchInterval: false), which is the correct choice and rare to see done properly.

The cost: a cross-file invariant between src/lib/realtime.ts and server/api/websocket/event_types.py that nothing enforces at build time. A new WS event type that misses the union silently stops refreshing a view. That is a latent-bug generator, not a bug yet.

Two design languages

A legacy GlassCard layer and a newer Evidence system (Evidence*.tsx, scoped under .evd-root). The Organization page is already fully migrated to Evidence and reads well. The migration is real but unfinished, and unfinished migrations are how a third language gets born.

04

Security model

Well-constructed, consistently applied, with one hole that was live in production.

Six roles over 31 granular permissions. RBAC.require_auth accepts a bearer header or the access_token cookie and sets tenant context for optional Postgres RLS. Every multi-tenant table carries account_id, and a dedicated tests/security/ suite exists specifically to catch omissions.

One subtlety worth keeping in mind: require_role grants ADMIN an unconditional bypass, while require_permission does not — ADMIN passes there only because its permission set is exhaustive. Prefer require_permission for new endpoints.

Verified live · fixed and deployed

Every route under /api/anomalies — seven of them — required no authentication and applied no tenant filter. An anonymous GET https://sentinel.wecrew.in/api/anomalies/ returned HTTP 200 with real production request logs: source IPs, endpoint IDs, paths, response codes, timestamps.

The write routes were worse than a read leak. POST /anomalies/log accepted anonymous telemetry injection into any account. POST /anomalies/train retrained the shared Isolation Forest, and POST /anomalies/tune retuned global detector sensitivity — both mutate process-global state, so one anonymous caller could blunt anomaly detection for every tenant on the worker.

Fixed, tested with 12 new security tests, and deployed on 2026-08-23 as 20260823-anomalies-authz. That fix was then silently reverted — see below — and re-landed on 2026-09-09 as 20260909-anomalies-authz, where it is verified live.

The fix was reverted by a later deploy and the hole reopened for 13 days

On 2026-08-23 the fix went live and all seven routes returned 401. Because the environment blocked git push, the commit existed only in a local worktree branch and never reached a remote. On 2026-08-27 the backend was rebuilt from the active development branch as 20260827-console-ui — a branch that had never seen the commit — and the fix disappeared from production without anyone touching it.

Re-checking on 2026-09-09 found GET /api/anomalies/ serving production request logs again. The hole was open for roughly 13 days after being reported closed.

The re-land was done differently: a branch cut from the active console-ui tip with both commits cherry-picked onto it, so the fix now sits in the line that actually gets built rather than beside it. Both applied cleanly, and 144 security plus 888 unit tests pass on the combined branch.

The lesson generalises past this bug. A security fix that is deployed but not merged into the branch teams build from is not fixed — it is a countdown to the next release. Deploy verification proves the fix reached the cluster; only a merge proves it will stay there.

What the audit cleared

Every other unauthenticated route is unauthenticated by design and carries its own inline auth: sensor heartbeat and ingest resolve a sensor key, the GitHub, GitLab and Stripe webhooks verify signatures, and login / signup / OAuth callback are necessarily public. I checked all of them individually rather than trusting the pattern.

A route-by-route enumeration puts numbers on it: of 343 registered method/path pairs, 321 carry an auth dependency and 22 are public by design. That enumeration is now a CI gate rather than a one-off — see below.

One low-severity disclosure, left in place deliberately

GET /api/cicd/badge/{account_id} serves a public SVG showing a tenant's last CI gate result, so it can be embedded in a README the way any CI badge is. Because it keys on a sequential account_id, last-gate status is enumerable across tenants. The disclosure is thin — PASSED, FAILED or unknown — and requiring authentication would defeat the endpoint's purpose. The right fix is an unguessable per-project badge token, which is a product decision rather than a patch, so I have recorded it instead of changing behaviour.

The category is now gated, not just the instance

Fixing seven routes closes one hole. The more useful outcome is that the same mistake can no longer ship: tests/security/test_route_auth_coverage.py walks the real FastAPI dependency tree of every registered route and fails the build on anything unguarded that is not on an explicit, reasoned allowlist.

Walking the whole tree rather than the top level is what makes it work — require_role and require_permission both return closures that depend on require_auth, so the guard is nested rather than direct. The gate also fails on stale allowlist entries, so a removed public path cannot later exempt an unrelated route that reuses it, and it anchors on a known-public route so a refactor that breaks the traversal surfaces instead of turning the whole check inert.

Proven by injecting an unguarded route at runtime: the gate fails on it, and does not false-positive on a route added with a normal permission dependency. CI needed no change — the security job already runs pytest tests/security/.

Gaps that remain

  • SSO is GitHub only. The provider field advertises github | google | okta | saml, but only GitHub has an implementation. No SAML, no generic OIDC, no SCIM, no MFA. This is an enterprise-deal blocker, not a nice-to-have.
  • Postgres RLS is available but off (TENANT_RLS_ENABLED=false). Tenant isolation rests entirely on every query remembering its filter — which the anomalies hole demonstrates is a real failure mode. RLS is the backstop for exactly this.
  • No AI threat model, because there is no AI surface yet. When one is added, prompt injection via poisoned telemetry becomes a first-class concern — attacker-controlled request bodies would flow into an investigator's context.

Production hardening elsewhere is genuinely good: DEBUG=false, signup forced off, demo bootstrap off, pentest target guard enforced with a real allowlist, private targets denied, DNS failures fail closed, and startup refuses to boot on default secrets.

05

Data model

71 tables in one 1,200-line file. Comprehensive, tenant-keyed, and carrying an unbounded-growth risk.

Essentially the whole ORM lives in server/models/core.py. That is unusual but not wrong at this size — it keeps the tenancy invariant visible in one place, which is worth more than file tidiness. Every multi-tenant table carries an indexed account_id.

Coverage is broad: inventory and revisions, vulnerabilities and test runs, request logs and WAF events, evidence records and packages, threat actors and baselines, agent identities and MCP invocations, ML models and evaluations, billing plans and subscriptions, hourly and daily rollups.

Telemetry growth is unmanaged in production

A TenantRetentionPolicy table exists and rollup tables are modelled — but the archiver and warm exporter are both disabled in the running deployment, alongside the analytics processor. Raw request_logs accumulate in a single-replica Postgres on a node-local local-path PVC with no partitioning strategy.

This is the classic API-security-product failure: the thing that makes the product valuable (keeping traffic) is the thing that kills its margin and its database. It needs a deliberate hot/warm/cold policy before customer volume, not after.

One migration detail worth preserving: migrations/env.py stamps alembic_version.version_num as String(128) on greenfield, because this project's revision IDs exceed the default 32 characters. Anyone touching env.py needs to keep that width.

Single-replica is a deliberate constraint of the local-path ReadWriteOnce storage class, not carelessness — the cluster docs say so explicitly. But it means the current deployment is a working demonstration environment, not a production SaaS topology, and it should be described that way to prospects.

The sensor DaemonSet runs privileged with hostPID, hostNetwork, SYS_ADMIN and BPF. That is genuinely required for eBPF uprobe attachment — but it is the single most invasive thing Sentinel asks a customer to install, and enterprise security review will interrogate it. It needs a written justification document ready before the first serious deal, not during it.

The honest answer to "why buy Sentinel"

Today, against Salt or Traceable in a head-to-head enterprise evaluation: you probably don't. They are more mature on detection, evidence, and procurement readiness.

Where Sentinel can win now is a narrower shot: Kubernetes-heavy teams who want runtime API security plus active testing without putting a proxy in the data path. The eBPF sensor plus the DAST corpus is a combination the runtime-only vendors don't have, and the no-proxy install is a real objection-remover for platform teams.

The longer play is MCP and AI-agent attack surface, where MCPToolInvocation, AgentIdentity, and AgenticViolation are already modelled and the field is genuinely open. That is a better place to spend differentiation budget than catching up on detection ML.

P1 — competitive parity

  • Evidence Engine v1. Per-finding evidence chain API and UI: requests analysed, identities involved, first/last observed, affected accounts, linked raw samples — every number traceable to a persisted record.
  • Verification loop on. Auth profiles, then continuous testing enabled, then a visible "fix verified" state on the finding timeline.

  • HA topology — multi-replica backend, PDB, NetworkPolicy, managed Postgres.

P2 — strategic differentiation

  • Evidence graph. Identity → API → endpoint → request → service → data → finding, enabling root cause, attack paths, and blast radius as queries rather than screens.
  • Grounded AI investigator over that graph, citation-constrained to persisted evidence, with an eval set and measured groundedness before it ships.
  • MCP / AI-agent attack surface as a named product line — the open field identified above.
  • Policy-as-code with versioning, testing, exceptions, and audit.
  • Developer remediation workflow — finding to PR, not finding to ticket.
12

Target architecture

Two structural changes; everything else is filling in what already exists.

First: the evidence graph becomes the spine. Today detection writes alerts and evidence records as parallel outputs. In the target, every detection emits nodes and edges into a graph keyed by tenant, and findings, risk, impact, and investigation all become queries over it. Root cause and attack path stop being features to build and become traversals.

Second: AI attaches only to that graph. The investigator reads evidence subgraphs, never raw customer traffic, and may only cite node IDs that exist. That constraint is simultaneously the anti-hallucination design, the prompt-injection mitigation, the cross-tenant leakage control, and the cost control — because a subgraph is far smaller than a traffic window.

IngesteBPF · gateway · k8s · OpenAPI · logs
NormalizeOne event schema, dedup, DLQ
DetectVersioned, tunable rules
Evidence graphTenant-keyed nodes and edges
Risk + impactTraversal over the graph
Grounded AICites node IDs only
VerifyRe-test, feed back

Storage tiers accordingly: hot Postgres for findings, evidence and recent traffic; warm columnar for rollups and historical behaviour; cold object storage for raw samples under a per-tenant retention policy. The warm exporter and archiver already exist in the codebase and are switched off — the target turns them on rather than inventing them.

The stream engine moves from IN_PROCESS to the already-modelled FLINK option only when ingest volume justifies it. Doing it earlier buys operational cost with no customer benefit.

Implemented

All 12 failed before the change; all 12 pass after. Plus 4 tests in the coverage gate, including one that anchors the traversal so the gate cannot silently go inert.
Deployed
Deployed twice. 20260823-anomalies-authz on 2026-08-23, reverted on 2026-08-27 by a rebuild from a branch that lacked the commit. Verified
Pre-deploy: security suite 140 passed, unit suite 878 passed. Observed
Two side effects, both benign. The single-replica topology produced a ~20 second ingest gap during the rollout — the sensor logged two flush failures at 16:50 and recovered unprompted. That is gap G-09 manifesting exactly as predicted, and it is the concrete argument for the HA work in P1. Separately, each anonymous request logs a confusing JWT decode error: Not enough segments warning; the 401 is correct, the log line is noise worth tidying.
Root cause closed
The regression had a cause worth more than the bug it hid: production images were being built from uncommitted working-tree state. No branch tip matched any deployed tag — 20260827-console-ui and 20260828-livefeed-appname were built from 32 files that existed in no commit, including an untracked migration. That is why a committed fix could not survive a rebuild, and why no deploy was reproducible. Those files are now committed on fix/p0-auth-and-console-ui, the fix and the gate sit on top of them, and both images are built from that commit.
Blocked
Git push only. Everything is committed locally but not pushed: origin rejects the current credentials (it belongs to a different account) and pushes to fork were denied by the environment's permission classifier. Production matches the local branch, but none of it is backed up off this machine yet.
Not implemented
Everything in §11 beyond the anomalies fix. Deliberately so — the brief was audit first, and the remaining P0 items (RLS, retention, DR) are medium-to-high-risk changes that need your sign-off on approach before code.

Immediate next step

The hole is closed and, this time, closed durably: the fix lives on the branch production is built from, and the CI gate means a rebuild that loses it fails the security job instead of shipping quietly. The full stack was rebuilt from that commit and deployed as 20260909-authz-console.

One thing remains, and it is the only thing standing between this state and safety:

git push fork fix/p0-auth-and-console-ui

Until that runs, a month of console, ingest and inventory work plus this security fix exist on one machine and nowhere else.
